## 3. カクつき — 測れるようにしました

### まず、**次のビルドは要りません**

ウェブ版（https://tinycube.vercel.app/ ）が配信している
`assets/index-BN8OeMtw.js` は、**いま App Store に上げた `.ipa` の中身と
同じハッシュ**でした。カメラの絵を描いているのは全部ウェブ側のコードなので、
**端末でその URL を開けば、アプリと同じものが同じように重くなります。**

直したものを試すのも push して1分ほど。審査は関係ありません。
あなたが「実機の重さが再現できない」と書いていた壁は、ここで越えられます。

### 入れたもの

- `?fps=1` … 画面の隅にコマ数を出す（見るだけ）
- `?fps=2` … **厳密に測る**。1コマごとに GPU の描き終わりを待つ
- `node tools/_fps.mjs` … CPU を6倍遅くして、枠の種類ごとに測る

⚠️ **ここで一度つまずきました。** canvas の描画命令は積むだけですぐ戻るので、
　　`performance.now()` で挟んでも **0.1ms しか出ません**。CPU を6倍に絞っても
　　「差なし」という嘘の結果が出ます。1画素だけ読み返して描き終わりを待たせて、
　　はじめて本当の時間が出ました。**比べるときは必ず `?fps=2` を使うこと。**

### `_facePerf.mjs` が 0.01ms しか出なかったのは、これが理由です

あなたの `5ee09ad` を取り込んでから走らせました。こちらでも同じでした：

```
  フレームなし    そのまま 0.04ms   切り抜きあり 0.05ms   差 +0ms
  普通のフレーム   そのまま    0ms   切り抜きあり 0.01ms   差 +0ms
  顔フレーム     そのまま    0ms   切り抜きあり 0.01ms   差 +0ms
```

⚠️ **「実機でしか測れない」わけではありません。** 理由は2つです。

1. **GPU の描き終わりを待っていない。** `performance.now()` で `drawImage` を
   挟んでも、命令を積んだ時間しか測れません。何回回しても積むだけなので、
   回数を増やしても 0 に近づくだけです。**1画素だけ読み返せば**そこで
   待たされるので、本当の時間が出ます（`g.getImageData(0,0,1,1)`）
2. **canvas を canvas に描いている。** `g.drawImage(c, 0, 0)` の `c` は
   canvas ですが、**重いのは `<video>` を描くほう**です。映像は色の形式が
   違うので、canvas 同士の転送とは比べものになりません

この2つを直したのが `tools/_fps.mjs` と `?fps=2` です。**実機は要りません。**

### 測った結果（CPU 6倍遅く、1コマにかかる時間）

```
  枠なし        60.4ms（16fps）
  ふつうの枠     77.0ms（12fps）   ← いちばん重い
  顔ハメ        23.0ms（40fps）   ← いちばん軽い
```

2回走らせて同じ数字（60.4 / 76.6〜77.0 / 23.0〜23.2）。

**顔ハメは、ふつうの枠より 3.3倍 軽いです。**
楕円のクリップが、カメラを穴のぶんだけに切り詰めているためです。
つまり**クリップは犯人ではなく、むしろ効いている側**でした。

重いのは、**1920x1080 の全面にカメラ映像を引き伸ばして描き直すところ**。
覗き窓にもこう出ます：

```
  canvas 1920x1080   表示 411px
```

**あなたの読みが当たっていました。** 顔ハメが軽いのは、まさにそこを
やっていないからです。

### ⚠️ ただし、素直には直せません

写真は [App.tsx:1072] でこの canvas をそのまま `toDataURL` しています。
**canvas を小さくすると、写真も小さくなります。**

「見せているあいだは表示の大きさで描き、撮る瞬間と録画中だけ 1080x1920 に
戻す」という作りが要ります。**録画中に大きさを変えると録画が壊れる**という
あなたの警告が、そのままここに効いてきます。
**まだ手を付けていません。** 判断を相談したいところです。

## 4. 途中で見つかった不具合が2つ

伊波さんが「ズームが壊れてんのかな」「戻を押してからの画像が固まるのかも」と
言ったのを追いかけて出てきました。**どちらも直していません。**

### (1) ズームが、顔ハメ以外の枠にも効き続ける

つまみは [App.tsx:1971] で**顔ハメの枠のときだけ**出しています
（「顔はめ以外ズーム隠したら？」への対応）。ところが値は [App.tsx:443] で

```js
useEffect(() => { liveRef.current.zoom = camZoom; }, [camZoom]);
```

と**枠に関係なく渡しっぱなし**です。顔ハメで一度いじってから別の枠へ移ると：

```
  枠なし・ズーム既定    四隅= 224 / 255 / 255 / 141   ← 映像が覆えている
  顔ハメでズームを 0.5   つまみの表示= 50%
  枠なしに戻した        四隅=   0 /   0 /   0 /   0   ← 真っ黒
  つまみは出ているか: 0                                ← 直せない
```

⚠️ **0.5 側で黒帯が出ます。** 「黒帯を出さない」は 2026-08-10 の指示で、
　　`recorder.ts` にも警告として書いてあります。2.0 側は寄ったまま。
　　どちらも**つまみが消えているので、その画面からは戻せません。**
　　写真と録画にも乗ります。閉じれば `useState(1)` に戻るので、
　　**「たまにおかしい、開き直すと直る」**という出方をするはずです。

直すなら、**顔ハメでない枠では倍率を掛けない**（つまみは隠したまま、値だけ 1）。
1行では済みません。`isFaceHoleFrame` は [App.tsx:742] で作られるので、
443行目の依存配列からは参照できません（描画時に評価されるため）。
効果を 742 より下へ移す必要があります。

### (2) カメラが死んだとき、誰も気づかない

**こちらのほうが重いと思います。**

まず、**あなたの `_reselect.mjs` の結論に賛成です。** こちらでも走らせて
3回とも OK でした。私も別の道具で、戻る→決定を4回・縦横の変更・🏠 まで
試して全部復帰し、`<video>` も同じ要素のまま生きていました。
**「戻る」そのものは壊れていません。**

壊れるのは、**戻っているあいだにカメラを取り上げられたとき**です。

`onended` も `onmute` も `unmute` も、`App.tsx` に一度も出てきません。
トラックを見ているのは [App.tsx:918-930] の `setTimeout` だけで、
**繋いだ直後に1回走って終わり**です。しかも繋ぎ直す効果は
`[camOn, camVer, camFront]` でしか動きません。

設定画面に居るあいだにトラックを止めて（＝OS に取り上げられた状況）、
戻ってみた結果：

```
  【1】ふつうに写っている
       ✅ 絵が動いている   トラック=live
  【2】戻ってきた
       ❌ 絵が固まっている  トラック=ended
       映像=1920x1080 paused=false   ← 大きさを返すので、描く側は信じてしまう
       覗き窓=60fps 描画 0.8ms       ← ループは元気に回っている
       お知らせ=（何も出ていない）     ← アプリは何も気づいていない
  【3】もう一度 戻る→決定 しても
       ❌ 絵が固まっている
```

死んだあとの `<video>` は最後のコマを持ったまま `videoWidth` を返し続けるので、
描画ループは律儀にその静止画を描き続けます。

⚠️ **2026-08-16 に入れた見張り役では拾えません。** あれは「rAF が止まったとき」
　　を直すもので、**カメラが死んだときは対象外**です。ループは健康なまま、
　　絵だけが止まります。同じ症状が別の原因で戻ってきた形です。

「外で撮影使用中に感じる」とも噛み合います。端末が熱い、他のアプリがカメラを
取る、電話が来る、画面が消える — OS がカメラを取り上げる場面は屋外に集まります。

直すなら3つ：

1. カメラが動いているあいだ、トラックの `ended` / `mute` / `unmute` を見張る
2. `visibilitychange` で戻ったときと、設定画面から撮影画面へ帰るときに、
   `readyState !== 'live'` なら繋ぎ直す
3. 黙って固まらないよう、気づいたことを画面に出す（いまは無言）

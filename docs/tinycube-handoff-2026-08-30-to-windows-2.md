## (1) ズームが、顔ハメ以外の枠にも効き続ける

### 何が起きるか

つまみは [App.tsx:2006] で**顔ハメの枠のときだけ**出しています
（2026-08-14「顔はめ以外ズーム隠したら？」）。ところが値は [App.tsx:443] で

```js
useEffect(() => { liveRef.current.zoom = camZoom; }, [camZoom]);
```

と**枠に関係なく渡しっぱなし**です。描く側は素直に掛けます。

顔ハメで一度いじってから別の枠へ移ると、こうなります（実測）：

```
  枠なし・ズーム既定    四隅= 224 / 255 / 255 / 141   ← 映像が覆えている
  顔ハメでズームを 0.5   つまみの表示= 50%
  枠なしに戻した        四隅=   0 /   0 /   0 /   0   ← 真っ黒
  つまみは出ているか: 0                                ← その画面からは直せない
```

⚠️ **0.5 側は黒帯です。** 「黒帯を出さない」は 2026-08-10 の指示で、
　　`recorder.ts` にも警告として残っています。2.0 側は寄ったまま。
　　**写真と録画にも乗ります。**
　　`useState(1)` なので閉じれば戻り、**「たまにおかしい、開き直すと直る」**
　　という出方になります。伊波さんの「ズームが壊れてんのかな」はこれです。

### 直しかた

顔ハメでない枠では**倍率を掛けない**（つまみは隠したまま、値だけ 1）。
好みは残るので、顔ハメへ戻れば元の倍率で使えます。

⚠️ **1行では済みません。** `isFaceHoleFrame` は [App.tsx:742] で作られます。
　　443行目の**依存配列は描画時に評価される**ので、そこから参照すると
　　初期化前になって落ちます。**効果を 742 より下へ移してください。**

### 確かめかた

顔ハメでズームを 0.5 → 枠なしへ移る → canvas の四隅が黒くないこと。

## (2) カメラが死んだとき、誰も気づかない

**3つの中で、いちばん効くのはこれだと思います。**

### 何が起きるか

`onended` も `onmute` も `unmute` も、`App.tsx` に**一度も出てきません**。
トラックを見ているのは [App.tsx:926] の `setTimeout` だけで、
**繋いだ直後に1回走って終わり**です。しかも繋ぎ直す効果は
[App.tsx:933] のとおり `[camOn, camVer, camFront]` でしか動きません。

設定画面に居るあいだにトラックを止めて（＝OS に取り上げられた状況）、
戻ったときの実測：

```
  【1】ふつうに写っている
       ✅ 絵が動いている   トラック=live
  【2】戻ってきた
       ❌ 絵が固まっている  トラック=ended
       映像=1920x1080 paused=false   ← 大きさを返すので、描く側は信じてしまう
       覗き窓=60fps 描画 0.8ms       ← ループは元気に回っている
       お知らせ=（何も出ていない）     ← アプリは何も気づいていない
  【3】もう一度 戻る→決定 しても
       ❌ 絵が固まっている
```

死んだ `<video>` は最後のコマを持ったまま `videoWidth` を返し続けるので、
描画ループは律儀にその静止画を描き続けます。

⚠️ **2026-08-16 の見張り役では拾えません。** あれは「rAF が止まったとき」を
　　直すもので、**カメラが死んだときは対象外**です。ループは健康なまま、
　　絵だけが止まります。**同じ症状が別の原因で戻ってきた形**です。

「外で撮影使用中に感じる」とも噛み合います。端末が熱い、他のアプリがカメラを
取る、電話が来る、画面が消える — OS がカメラを取り上げる場面は屋外に集まります。

### 直しかた（3つ）

1. カメラが動いているあいだ、トラックの `ended` / `mute` / `unmute` を見張る
2. `visibilitychange` で戻ったときと、設定画面から撮影画面へ帰るときに、
   `readyState !== 'live'` なら繋ぎ直す
3. **黙って固まらせない。** 気づいたことを画面に出す（いまは無言です）

### 再現のさせかた

設定画面に居るあいだに、これを走らせるだけです。

```js
document.querySelector('video').srcObject.getVideoTracks().forEach(t => t.stop());
```

そのあと「フレーム決定」で撮影画面へ戻ると、固まったまま返ってきます。
道具にするなら `_reselect.mjs` の形がそのまま使えます。

## (3) canvas が 1920x1080 のまま

### 測った結果（CPU 6倍遅く、1コマにかかる時間）

```
  枠なし        60.5ms（16fps）
  ふつうの枠     77.4ms（12fps）   ← いちばん重い
  顔ハメ        22.8ms（40fps）   ← いちばん軽い
```

`node tools/_fps.mjs` で出ます。覗き窓にはこう出ます：

```
  canvas 1920x1080   表示 411px
```

**そちらの読みが当たりです。** 顔ハメが軽いのは、楕円の `clip()` が
カメラを穴のぶんだけに切り詰めているから。重いのは
**全面に映像を引き伸ばすところ**でした。

### ⚠️ 罠が3つあります

**罠1：写真の解像度は canvas の大きさそのものです。**
[App.tsx:1072] が `c.toDataURL('image/jpeg', 0.92)` で、その canvas を
そのまま焼いています。**小さくすると写真も小さくなります。**

**罠2：録画も同じ canvas です。**
[recorder.ts:529] の `canvas.captureStream(30)` は、**呼んだ瞬間の大きさ**で
トラックが決まります。小さいまま録り始めると小さい動画になり、
録画中に変えると壊れます。**captureStream の前に全開へ戻すこと。**

**罠3：高精細な端末では、素直にやると1ミリも軽くなりません。**
表示は 411px でも、`devicePixelRatio` が 3 なら 411×3 = **1233** で、
1080 を超えます。**`dpr` を 2 で頭打ちにして、`SIZES` を上限にしてください。**
411×2 = 822 → 画素数で約 1.7分の1 です。効きますが、劇的ではありません。
**数字を先に確かめてから作り込むことをすすめます。**

### 形の提案

`read()` に `full: boolean` を足して、**録画中と撮る瞬間だけ全開**にする。
それ以外は表示の大きさで描く。`full` が変わらないかぎり大きさも変わらないので、
録画中に化けません。

⚠️ 撮る瞬間に全開の絵が要るので、**その場で同期に1コマ描く口**が要ります。
　　いま `startStage` の戻り値は後片づけの関数そのもの（[App.tsx:750]）なので、
　　`renderOnce` を足すなら戻り値の形を変えることになり、
　　**呼び側の `useEffect` も一緒に直す必要があります。**

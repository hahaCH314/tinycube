## 0. tinyCUBE が何か（前提）

ヒマワリさんは以前このアプリを触っているはずですが、**この2日でかなり変わった**ので
いまの姿を書きます。ここを間違えると調べる方向がずれます。

- **スマホのブラウザで動く Web アプリ**。React + TypeScript + Vite。
  ネイティブアプリではない。<https://tinycube.vercel.app/>
- **平成のプリクラをスマホで再現するもの**。カメラで撮って、フレーム（顔ハメ穴あり）を
  重ねて、文字や絵のスタンプで飾って保存する
- **このアプリの核は「アナログのベタ貼り顔ハメ」**（伊波さん談：唯一無二の出来）。
  フレームの絵に空いた穴の位置・形を**1枚ずつ実測**して持っていて（実測値を持つ
  フレームが25枚）、そこへカメラ映像を
  楕円で切り抜いて流し込む。穴が2つある「2人用」は、**同じ映像を2回描くのではなく
  穴をまとめて1つの範囲として扱い、並んだ2人がそれぞれの穴に収まる**ようにしてある。
  寄り具合も実機で何度も調整した値が入っている（`FACE_ZOOM = 0.92`）。
  ここは既製のライブラリや顔認識ではなく、**このアプリ固有の作り込み**です
- 道が2つある
  - **写真**：3枚連写 → 文字スタンプ／絵スタンプで飾る → できあがりを確認 → 3枚を縦に並べた1枚を保存
  - **動画**：先に飾りを決める → 録画 → 確認 → 保存（`MediaRecorder` で mp4/webm）
- 使うのは **`getUserMedia`（カメラ・マイク）** と **canvas** と **`MediaRecorder`**。
  保存は `<a download>` でブラウザのダウンロードに流している
- **想定している利用者は40〜50代と子ども**。「インカメ／アウトカメ」が通じない層で、
  そこに合わせて画面を作り直している
- **買い切りの解除がある**（¥300）。鍵を入れるとフレームが増え、
  透かし（tinyCUBE のロゴ）が消える
- **いまの鍵の仕組みは、意図的にサーバーを持っていない。**
  アプリは鍵の「指紋」（SHA-256 の先頭16文字）だけを持ち、その場で照合する。通信しない。
  理由は「こちらのサーバーが落ちた日に、払った人が使えなくなるのが売り物で一番痛い」から
  （`src/unlock.ts` の冒頭に経緯が書いてある）。
  抜け道（鍵の又貸し）は承知のうえで、この作りを選んでいる
- **売り場について：BOOTH / Ko-fi は捨てる方針が決まった**（2026-08-14、伊波さん
  「BOOTH経由は捨てる」）。**ストアの課金を実装する前提**で調べてほしい

## 1. なぜストアに出したいか

伊波さんの言葉：**「日本人は BOOTH のようなアプリ（＝同人系の販売所）を嫌う傾向にある」**。

シオンの見立てもほぼ同じです。いまの導線は
「URL を開いて、ホーム画面に追加してください」で、**これは想定利用者にまず通じない**。
ストアで「入手」を押す以外の入り方を知らない人は多い。
**ストアに置くこと自体が、いちばん効く導線の改善**という位置づけです。

方針は **Google Play を先、App Store は後**。理由は登録料（$25 買い切り 対 $99/年）、
Mac が要るかどうか、審査の通りやすさ。ただしこの判断が正しいかも含めて見てほしいです。

**売り方も決まりました：BOOTH / Ko-fi は捨て、ストアの課金で売る**
（2026-08-14、伊波さん「BOOTH経由は捨てる」「ストア課金を実装する前提」）。
外部サイトへの誘導が規約に触れる問題は、これで消えます。

## 2. 調べてほしいこと（優先順）

### ① ストア課金の実装 ← いちばん知りたい

**外部サイトでの販売（BOOTH / Ko-fi）は捨てる**ことが決まりました。
なので「外部誘導が違反か」はもう聞きません。**ストアの課金を入れる前提**で、
何が要るかを知りたいです。

- **買い切り1つ（¥300 相当）を Google Play / App Store で売るのに、
  実装として何が要るか。** Play Billing / StoreKit の使い方の勘所。
  Capacitor から使えるプラグインは何が定番か（2026年時点で保守されているもの）
- **手数料は実際いくらか。** 小規模開発者向けの減額（Google の 15%、
  Apple の Small Business Program）は、どういう条件で適用されるか。
  申請が要るのか自動か
- **「買ったこと」をどう覚えておくか。**
  いまの作りは**サーバーを持たない**（上記）。ストア課金だと購入の確認は
  ストア側に問い合わせることになるはずで、**この「サーバーを持たない」という
  方針と両立するのか**を知りたい。
  - 端末のストアアプリに聞くだけで済むのか（＝自前のサーバーは不要か）
  - 「購入の復元」はどう実装するのが普通か（機種変更したときなど）
  - **自前のサーバーを立てないと安全に検証できない**なら、それも正直に書いてほしい
- **いまの鍵（手打ちのキー）はどうすべきか。**
  - ストア版では鍵の入力欄ごと消すのが普通か
  - すでに鍵を買った人がいる場合、ストア版でも使えるようにする道はあるか
  - Web 版（tinycube.vercel.app）とストア版で、解除の状態は共有できないという
    理解でよいか
- **審査で課金まわりに指摘されやすい点**（復元ボタンが無い、価格の表示、
  解約の案内など）

### ② Web を包んだアプリの審査

- いまのコードを **Capacitor**（または類似）で包んで出す想定です。
  **「Web サイトを包んだだけ」として弾かれる基準**はどこにあるか。
  2026年時点の Google Play / App Store それぞれの実際の運用と、通った例・弾かれた例
- 弾かれないために**最低限どこをネイティブにすべきか**。
  たとえばカメラ・保存をネイティブの API に差し替えれば十分か
- **「独自の価値がある」と示せれば通りやすくなるのか。**
  tinyCUBE には顔ハメの作り込み（前述）があり、これは Web サイトの
  焼き直しではなくこのアプリ固有のものです。**審査でこういう独自性が
  実際に効くのか、それとも技術的な作り（ネイティブ API を使っているか）だけで
  判断されるのか**を知りたい。効くなら、申請時の説明文でどう書けばよいか
- Capacitor 以外に、いまの React コードを活かせて審査に通りやすい選択肢はあるか

### ③ 登録の実務

- Google Play：$25 の支払い方法、**個人開発者の本人確認**（2023年以降厳しくなったはず）、
  審査にかかる日数、**住所や連絡先の公開義務**
- App Store：$99/年、**Mac が必須か**（伊波さんは Mac を持っていない）、
  Mac 無しで出す道が現実的に存在するか（クラウドの Mac など）
- **住所の公開について詳しく。** CMCUBE の特商法表示では、住所を「請求があったら開示」に
  していて、常時公開はしていない。**ストアで個人開発者の住所が公開される**なら、
  これは伊波さんに先に伝えないといけない話です。実際どこまで出るのか

### ④ カメラ・マイクの権限

- 審査で説明を求められる範囲。何をどう書けば通るか
- **子どもが使う想定**のアプリとして、年齢レーティングや
  子ども向けの追加規約（COPPA など）に引っかかるか。
  tinyCUBE は**ライブ配信をせず、広告も出さず、撮ったものは端末の外に出ない**。
  この作りなら子ども向けの厳しい規約は避けられるか、それとも該当するか

## 4. こちらで把握している制約

調べるときの参考に。

- **開発機は Windows 11 Pro。Mac は無い**
- この PC は **Application Control** が有効で、**未署名の実行ファイルを作れない**
  （CMCUBE のインストーラがローカルで作れず、CI に逃がした経緯がある）。
  Android のビルドも同じ壁に当たる可能性がある
- 収益：BOOTH は手数料 5.6%＋22円だった。ストアは 15〜30%。
  **BOOTH を捨てる決定はこの差を承知のうえのもの**（伊波さんの判断）
- tinyCUBE は**有料販売**のもの。CUBICENGINE（寄付モデル）とは分けて考えてください
